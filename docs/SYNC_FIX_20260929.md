# 2026-09-29 报价、采购跨设备同步修复

## 根因与数据核对

- 原实现把整张表写进单个 `uni.setStorageSync` 项。微信端单项上限为 1 MB，实际报价明细约 1.38 MB、跟进约 2.47 MB，导致拉取时订单头更新成功、后续明细写入失败。
- “保存”原来只等待本机写入；下载与上传并发时，旧下载快照还可能覆盖已上传的修改。
- 只读核对截图中金凤幼儿园 2026-09-24 的报价：服务器仍有 34 条明细。没有执行清库、回滚或批量补造记录。

## 本次调整

- 大缓存分块写入；全部分块成功后才切换索引，失败保留旧快照。兼容原来的单项缓存。
- 上传、下载串行；先补传待同步记录，再下载；下载结果先合并未上传修改，再写缓存。
- 报价单、采购单、采购申请保存等待服务器成功回执。失败显示明确错误并保留待同步队列，重开、回前台、网络恢复时可以重试。
- 新采购明细在保存时关联订单；保留库存单位换算、已入库不可直接修改和采购明细合并规则。
- 报价详情金额跟随当前明细刷新；数量输入失焦时不立即展开新跟进，避免把正在点击的保存按钮挤走。

## 验证

- `node --test tests/*.test.mjs`：缓存超限、写入失败保护、连续修改、上传确认、下载/上传竞争和采购合并/单位换算。
- `node tests/e2e-save-sync.cjs`：通过真实浏览器操作与隔离的模拟接口，员工连续录入、延迟回执、断网重开补传、新建采购及申请、另一个管理员账号读取、合并预采购。测试不会写入生产库。
- `node tests/live-cache-readonly.mjs`：只读生产接口，在单项 1 MB、总量 10 MB 限制下写入缓存并模拟重开核对。625 张报价、2,896 条明细、5,108 条跟进通过，峰值约 8.03 MB。
- H5、微信小程序生产构建均需通过后才上传。

## 手机升级与验收

1. 上传完成后，在微信公众平台将对应开发版本设置为体验版，再让员工和管理员都进入新体验版。上传开发代码不等于已经切换体验版，也不等于发布正式版。
2. 不要清理旧手机缓存或删除小程序。先在旧设备联网打开新版，等待同步完成；对仍未同步的单据点击保存，确认“已保存到服务器”。
3. 管理员在另一部手机重新打开列表与详情，核对商品、数量、金额、跟进及采购申请汇总。
4. 本次确认的是缓存/同步链路；不能据此承诺所有历史未上传内容均已恢复。若仍有某张单据异常，保留原设备缓存并按单据逐条核对。

分块解决单项大小限制，不会绕过微信总缓存容量限制；总数据继续增长时仍需规划增量/按需拉取。
